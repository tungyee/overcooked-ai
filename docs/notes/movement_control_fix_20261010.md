# 柜台前停住与相邻站点震荡修复

## 原因

`trace-20261010-000033.jsonl` 中，P2 手持 SushiRice，站在 `(6, 2)`，
灶台位于 `(7, 1)`，选择的交互位是 `(6, 1)`。旧逻辑在距离小于
1.2 世界单位时始终松键并返回 RUNNING；角色已经停住也不会重新补步。
任务超时、订单切换后仍会对同一灶台重复这一过程。

直接恢复近处长按会重新引入 a—c—b 震荡：插件每 200 ms 推一帧，
控制循环每 50 ms 跑一次，重复使用旧位置时持续输入，容易滑过交互位。
两者分别是 5 Hz / 20 Hz。修复保留这两个频率，明确区分观测和控制时钟。

## 实现

- `StateClient.read_latest()` 排空当前积压的完整帧，仅返回最新合法帧，保留不完整尾部。
- Agent 仅在收到快照时推进 `frame_seq`，复用旧快照的循环拍不算新观测。
- `Approach` 锁定可达交互位；剩余路径两步以内使用 50 ms 短按。
  接近目标、转弯、折返都先松键，至少等待 150 ms 和一张新快照。
  普通地面位置仍明显变化时继续观察；新帧显示站住但尚未到位时继续补步。
- `Face` 同样采用短按与新帧反馈，以真实交互朝向判断成功。
- `InteractWith` 记住 Approach → Face → Tap → Confirm 的阶段。
  按键或确认期间不重新走路，拾取后源物品先消失也继续等待后置条件。
  `EnsureHandsFree` 的地板落点也共用移动控制。
- `Controller.tap()` 不再阻塞主循环。方向短按、拾取和顶带键都有独立松键定时器；
  旧定时器不能释放抢占后新按下的键。任务 halt 会取消未完成的按键。
- `Confirm` 在正式运行时按新快照消耗重试预算，并有实际时间上限。
- 连续无进展会退出移动并按位置、资源短暂避让，订单变化不能绕过该记录。
  断流超过 750 ms、暂停、离开关卡或退出进程均松键。
- 路径回溯使用与建场一致的 P1 周边软代价，避免将可达路线误判为断链。

位置、资源避让分别使用现有的 80 / 200 拍 TTL（4 / 10 秒），仅在 Normal
模式的移动无进展或观察超时上启用。没有修改资源认领写权或插件协议。

## 验证

全量：`python3 -m pytest tests/ -q --tb=short`，**792 passed, 35 skipped**。

- 最新 trace 的 tick 1032 裁剪状态固定为
  `tests/fixtures/motion/trace-stall-20261010.ndjson.gz`：验证真实坐标下朝 `(6, 1)`
  补步、旧帧松键、同坐标新帧继续补步。该样本缺 nodeMap，使用站点占用兜底；
  单独放在 motion 子目录，避免当成完整实机录帧驱动其他 fixture 测试。
- 36 组 20 Hz 控制 / 5 Hz 反馈模拟：不同初始距离、速度和滑行衰减，验证进入
  中间目标格且停稳后不滑出，包含远处持续移动转近处短按。
- 整棵 FetchToCooker 树模拟：持米走近、停稳、转向、下米，并验证锅开煮、手空、
  只发送一次拾取。
- 验证转弯刹停、到位后滑出重查、真实阻挡退出、任务重建不能在旧帧重复补步、
  断流松键、异步拾取与顶带截止时间、旧定时器取消、P1 避让代价回溯。

验证全程使用假控制器，没有向游戏注入真实按键。35 个跳过项仍依赖缺失的完整
实机 fixture 或其他原有环境条件。模拟参数覆盖不等于已测量游戏物理参数，
实机速度、碰撞与传送带效果需要下一局新 trace 复核。

## 生效与复盘

重启 Python AI 进程即可；本次未改 C# 插件，无需重新编译或重启游戏。

新 trace 的 `exec.observation` 记录收帧编号、帧龄，`exec.motion` 记录
`cruise / pulse / observe / arrived / failed`、是否新帧、目标格和交互位。
这能区分正常等待新观测、补步和真正无进展。
