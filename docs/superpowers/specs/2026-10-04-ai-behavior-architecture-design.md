# Overcooked! 2 AI 陪玩 —— 行为决策架构重新设计

> 日期：2026-10-04　状态：已过架构评审 + 代码事实核查（第 2 轮修订），待实施
> 范围：`ai/` 下的 Python 决策主体。**C# 插件与 socket 传输层本轮不改**；需改插件的关卡机制全部列入 §10 未来工作。
> 相关文档：`AGENTS.md`（项目说明）、`PLAN.md`（进度与技术笔记）、`AI_REVIEW.md`（上一轮评审与修复）。

## 1. 背景与目标

数据链路与控制链路已打通：BepInEx 插件 5 Hz 推送 NDJSON 状态，Python 进程（20 Hz 主循环）用行为树决策并通过 `CGEvent` 注入 P2 键盘。问题出在**行为设计不够明晰**：决策逻辑混杂、难以扩展。

本轮首要目标（已确认）：**行为能力优先**。架构必须承载以下四项能力：

1. **单厨师多订单穿插** —— 下锅煮饭的空档去切下一单的菜、合并同类采购。
2. **智能订单优先级** —— 综合剩余时间、分数、combo、完成度、料复用排序，取代当前"按 `remaining` 升序"的单一启发式。
3. **多锅 / 多切菜台资源管理** —— 哪口锅煮哪单、哪个板切什么。
4. **P1 协同与自动补位** —— 观察人类玩家，避免重复劳动与站位冲突，主动接管其下游工序。

同时作为显式设计目标：

- **预留对话协作层** —— 未来可用自然语言与 AI 商量分工、指派灭火等。本轮只预留注入口与读取逻辑，不实现语言解析。
- **决策可观测** —— 任何时刻可回答"为什么选这个动作而不是别的"。
- **不新增关卡硬编码** —— 见 §9。

非目标（本轮不做）：关卡机制适配（冰面、移动地板等，见 §10）、方案 B 进程内控制、对话层的自然语言解析。

## 2. 现状诊断

### 2.1 保留的部分

`world.py`（世界模型 + BFS 寻路）、`bt.py`（行为树引擎）、`controller.py`（键盘注入）职责清晰、质量良好，予以保留。

### 2.2 三个核心病灶

**病灶一：双范式打架。** 行为树与手写状态机（灭火 / 丢弃 / 卡住脱困）两套范式并存。更严重的是 `_build_tree()` 里的 `fire_branch` / `discard_branch` 是闭包，内部直接改写 `self.mode` / `self.sub` / `self.pot` / `self.plate_pos`——**真正的控制流不在树结构里，而藏在副作用里**。行为树只是外壳，读树读不出实际行为。

**病灶二：God Object。** `agent.py` 1180 行，一个类同时承担 socket 循环、决策、建树、约 20 个世界查询谓词、寻路、底层按键。`self.sub` 单个字段被灭火、丢弃、常规移动三套状态机共享，靠 `self.mode` 区分语义，极易串台。谓词方法内含副作用（`_station()` 写 `self.pot`，`_should_rush_cooked()` 写 `self.pot`），"查询"与"写状态"混同。

**病灶三：动作层大量复制与隐式耦合。** `actions.py` 747 行，"goto → tap → confirm" 模板在 15 处以上近乎逐字复制；`_tick_wash` 单方法 113 行。动作之间靠 `agent.pot_cooked` / `agent.dropped_cooked_pot` 等裸全局字段隐式传递交接状态，无契约、易漏置漏清。临时字段用 `getattr(self, ..., 0)` 懒初始化，生命周期不清。

### 2.3 根因

把两类性质完全不同的问题揉在了一起：

| 问题性质 | 例子 | 适合的范式 |
|---|---|---|
| **组合优化 / 规划** | 哪单先做、哪口锅煮什么、煮饭空档插什么活、P1 在干嘛 | 无状态纯函数，每拍重算 |
| **反应式执行** | 走过去、拿起、切、倒；被火情打断后续跑 | 状态机 / 行为树 |

行为树擅长按优先级反应，不擅长组合优化。把规划塞进树里，树必然膨胀成今天的样子。**重新设计的核心是把这两层劈开。**

## 3. 架构总览

分三层：**Arbiter（仲裁）→ Planner（规划）→ Executor（执行）**，外加 **Blackboard（黑板）** 作为唯一可变状态容器。

```
   游戏进程（C# 插件，本轮不改）
        │ NDJSON 5 Hz 全量快照
        ▼
   world.py: StateClient + World        （保留，增加 flood-fill 全图距离）
        │ 每拍一个 World 快照
        ▼
   Blackboard                            （新）
     资源认领 · 订单归属 · 当前承诺 · P1 模型 · 意图注入口 · 类型化 scratch
        │
   ┌────┴─────────────┬──────────────────┐
   ▼                  ▼                  ▼
 Arbiter           Planner            P1Model
 （状态机）        （步进函数）         （三层推断）
 三行模式表         候选→可行性→        事实 / 短程意图
 + 卡住守卫        协作过滤→打分→      / 显式告知
 选谁拿控制权       承诺惯性            + confidence 衰减
   │                  │
   │ 中断 task        │ Normal 模式下产出 task
   └────────┬─────────┘
            ▼
   Executor: task → 小行为树（复用 bt.py）
     叶子 = 带强制前后校验的原语
            ▼
   controller.py: CGEvent 注入 P2       （保留）
```

**数据流一句话**：World 快照 → 认领对账 → 更新 P1 模型 → Arbiter 选模式 → Normal 则 Planner 选 task、否则取中断 task → Executor tick 成按键 → 输出决策记录。

### 3.1 为什么是这个结构

- **Arbiter 就是最初设想的"状态机"**，但职责收窄为"谁拿控制权"，不负责"怎么做"。
- **Planner 是行为树做不到的那一层**，承载 §1 的四项能力。纯函数、可单测。
- **Executor 是"每个状态一棵行为树"的落点**，但树退化为几步线性顺序，因为决策已上移。

### 3.2 对话协作层的三个注入口（预留）

未来对话模块只需把自然语言解析成结构化意图写入 Blackboard，无需理解行为树或动作细节：

| 用户说 | 结构化意图 | 谁读它 |
|---|---|---|
| "你去灭火" | `{assign: fire, to: P2}` | Arbiter（`Assigned` 模式，硬覆盖打分） |
| "寿司你做，盖饭我来" | `{order: B, owner: P2}` | Planner（协作过滤） |
| "你多做点 / 你别乱动" | `{aggressiveness: high}` | Planner（打分权重） |

显式指令**优先于** P1Model 的推断：推断是"无指令时的默认协同"，指令是"有指令时的硬覆盖"。这是选择本架构的决定性理由——另两个候选方案（纯 HFSM+BT、Utility AI）都没有干净的意图注入点。

### 3.3 已评估并否决的方案

| 方案 | 否决理由 |
|---|---|
| 顶层 HFSM + 每模式一棵行为树 | 多订单调度仍挤在 `Normal` 树里，半年后重新膨胀；无集中意图入口，"讨论分工"这类影响全局分配的意图在纯 BT 里无落点 |
| Utility AI 全局效用打分 | 易抖、调参玄学、日志可解释性差；显式指令只能做成软加权，给不了"我说了就照做"的确定性 |

### 3.4 关键机制：传输维持全量快照

**两个频率不要混淆**（原设计稿曾误记为同一个值）：

| 频率 | 值 | 来源 |
|---|---|---|
| 插件推送 | 5 Hz | C# 侧 `InvokeRepeating` 0.2 s |
| Python 主循环 | **20 Hz** | `agent.py:88` `time.sleep(0.05)` |

即 Python 每约 4 拍才看到一帧新数据。本文档中"拍"统一指 **Python 循环拍（50 ms）**。两处后果：

- 所有以拍计数的阈值都要按 20 Hz 读。例如现有洗盘兜底 `confirm_wait >= 20`（`actions.py:198`）是约 **1 秒**，不是 4 秒。
- **同一帧会被决策多次。** Planner 每拍重算，但相邻 3-4 拍的输入完全相同，输出也必然相同——这是浪费，但无害（承诺惯性会让行为稳定）。可选优化：帧号未变则复用上拍决策，只继续 tick 执行层。列为 §11 阶段 7 的可选项，不在初版。

不改为事件 hook 推送，三条理由：

1. 改传输协议需动 C# 插件，与本轮约束冲突。
2. **快照自愈，事件流会状态漂移。** 快照丢一帧下拍自动补上；事件增量漏一个（插件队列满确实会丢帧，`AI_REVIEW.md` Bug#11）黑板就与游戏永久不同步。
3. **决策是无记忆的。** Planner 每拍拿全量世界重算，天然需要"当前完整状态"而非"增量变化"。

计算量已在 `AI_REVIEW.md` 优化项 2 量过：**17×13** 网格（实测帧 `nodeMap:"17x13=..."`，AI_REVIEW 记的 17×11 是旧数）单次 BFS 数百次操作，可忽略。

## 4. Blackboard（黑板）

**定位**：取代散落在 `Agent` 上的约 20 个跨拍字段。唯一的可变状态容器，**写入权受控**。

```
Blackboard
├── claims ——————————— 资源认领表（多订单并行的核心，动作级粒度）
│     key:   (resource_id, action)          ← 注意：不是 resource_id
│     value: {owner, order_id, claimed_tick, ttl}
│     waiters: { resource_id → [(order_id, since_tick)] }   等待队列
├── order_assignment —— 订单归属（分单模式用，持久化不每拍重算）
│     { order_id → "P1" | "P2" | None }
├── commitment ———————— 当前承诺（防抖）
│     active_task / started_tick / steps_done / infeasible_streak / retries
├── p1_model ————————— P1 推断（由 P1Model 写，详见 §6.7）
│     holding / p1_active_task / confidence / last_evidence_tick
├── intents —————————— 意图注入口（对话层预留，本轮为空壳）
│     assignments[] / collab_mode / role_constraint / aggressiveness
└── scratch ———————————— 中断模式局部状态（类型化，模式进入时构造、退出即丢弃）
      StuckScratch{bad_cells, nudge_dir, last_cell, same_count, skip_ticks}
      FireScratch{ext_target, bad_ext, tries}
```

**为什么 `scratch` 必须类型化**：§2.2 批判旧代码的核心罪状是"`self.sub` 单字段被三套状态机共享、靠 `mode` 区分语义"。若新设计用一个字段随用随加的无类型字典，那只是把同一个问题换了名字塞进黑板。因此：**每个模式一个显式类型的 scratch 对象，模式进入时构造、退出时丢弃，禁止跨模式复用字段。**

### 4.0 认领为什么是动作级粒度

这是整张表最关键的设计决定。若按**资源**粒度认领（`cooker_id → owner`），接力协作直接废掉：P1 往 1 号锅放了生饭，该锅被标记为"P1 占用"，AI 就不会去取熟饭——而取熟饭恰恰是最有价值的接力。

正确的规则是：**P1 的行为只锁住他正在做的那个动作，不锁住该资源上的其他动作。**

以"P1 刚往 1 号锅放了生饭"为例：

| 该锅上的待办动作 | 状态 | AI 该不该上 |
|---|---|---|
| 放生饭进锅 | P1 已完成 | 跳过（已完成，不是被占） |
| 等煮熟 | 锅自己 | 无需人 |
| **取出熟饭** | **无人认领** | **该上 —— 这就是接力** |
| 烧糊后丢弃 / 灭火 | 无人认领 | 该上 |

所以键是 `(resource_id, action)`。`(cooker1, "fetch_to")` 被锁时，`(cooker1, "take_cooked")` 依然开放。

### 4.1 认领生命周期（四个释放触发点）

设计稿初版只定义了认领的**建立**与**失效**，没有定义**释放**——后果是：灶 / 板 / 拼装格不会"消失"，故对账永远不清它们，订单送完后认领带着一个已不存在的 `order_id` 永久挂着，几轮之后资源全部楔死。必须明确四个释放点：

| 触发 | 规则 |
|---|---|
| **task 成功** | 该 task 持有的 `(resource, action)` 键**删除**；若存在下游动作则由下游 task 自行认领（不继承） |
| **订单消失** | `order_id` 不在当前订单表 → 该单所有认领全部释放（送达、超时过期、被 P1 抢先完成都走这条） |
| **资源消失 / 内容不符** | 认领的盘被端走、锅不见了、内容与 `contents_expected` 不符 → 失效 |
| **TTL 兜底** | 超过 `ttl` 拍仍未推进 → 强制释放。**这是防认领泄漏的最后一道闸**，任何前三条漏掉的情况都由它兜住 |

### 4.2 可行性必须读 claims（否则认领形同虚设）

设计稿初版的致命缺陷：定义了认领表，却**没有任何一条可行性谓词读它**。那么 claims 是一张只写不读的表，"多锅 / 多台资源管理"这项能力没有任何落地机制。

补一条**全局可行性前置**，作用于全部 task：

```
task 可行  ⟹  对其所需的每个 (resource, action)：
                该键未被他人认领   或   认领已过 TTL
```

这一条写在 §6.2 流水线的可行性过滤最前面，优先于各 task 自己的谓词。

### 4.3 等待与让出（分单模式的死锁防护）

分单模式下会出现"B 单要用锅，但 P1 的 A 单正占着"。设计稿初版写"靠 claims 排队"，但没有队列——而这是教科书式的 hold-and-wait：AI 为 B 单握着盘 + 拼装格等锅，P1 的 A 单若需要那个拼装格，双方互等。

三条规则：

1. **waiters 队列**：想用但被占时登记 `(order_id, since_tick)`，资源释放时按**等待时长**优先给（老化优先级，防饿死）。
2. **超时让出**：等待超过 `WAIT_GIVEUP_TICKS` 则放弃该 task，**并释放自己手上的其他认领**，重新规划。这一条直接打断 hold-and-wait 的成环条件。
3. **不为"将来"预留**：只认领当前 task 真正要用的资源。禁止提前占位。

### 4.4 资源标识的稳定性假设

对账完全依赖资源 id 跨帧稳定，故必须逐类说明 id 来源：

| 资源 | id 来源 | 跨帧稳定性 |
|---|---|---|
| 灶 / 板 / 洗碗池 | 站点实例名 `n` | **稳定**（固定设施） |
| 拼装格 | 网格坐标 `(gx, gz)` | **稳定**（坐标即身份） |
| 盘 | 实例名 `n` 为主、`(gx, gz)` 为辅校验 | **需验证** —— 见下 |

**盘的识别是已知风险点。** 若盘只能按位置识别，则"盘被端起移动"与"盘消失"在对账眼里无法区分，会误杀正被 P1 搬动的盘。两条防护：

- 优先用实例名 `n`；位置仅作交叉校验。
- 对账失效判定给**一拍宽限**（连续两拍都找不到才失效），吸收搬动过程中的瞬时缺失。

本条列为 §11 阶段 2 的单测断言：构造"盘被端起"帧序列，断言认领**不被**误杀；构造"盘真的消失"，断言认领被清。

### 4.5 写入规则（防串台的关键）

| 层 | 可写 | 不可写 |
|---|---|---|
| Planner | `claims`、`commitment` | 其余 |
| P1Model | `p1_model` | 其余 |
| Executor | `commitment.steps_done`、`commitment.retries`、`scratch` | **`claims`**（执行不做分配决策） |

Planner 虽然写 claims，但其本身是纯函数：它**返回**新的认领状态，由主循环写回黑板，自己不持有可变引用。

### 4.6 认领对账 `reconcile_claims(world, bb)`

每拍开始用新快照校验一次认领。认领的盘 / 锅若在世界中消失，或内容与预期不符（被 P1 端走、人类抢先出餐），**失效该认领**。Planner 下一步看到认领已清，自然重新分配。

这是"用户抢先出餐后 AI 自动改做下一单"的实现机制：订单被抢 → 认领失效 → 重分配。不需要满地找恢复逻辑。独立小函数，可单测。

### 4.7 与现有字段的映射

| 今天 | 新位置 |
|---|---|
| `self.pot` | `claims[(cooker_id, action)]` |
| `self.plate_pos` / `_my_plate`（"唯一有内容的盘"近似） | `claims[(plate_id, action)]`（显式认领，解决多订单下近似失效） |
| `self.pot_cooked` / `dropped_cooked_pot` | 不再需要（见 §6.1 第 5、12 号 task；前提是锅具识别修好，见 §9） |
| `self.stuck_*` | `scratch.StuckScratch` |
| `ext_target` / `bad_ext` | `scratch.FireScratch` |
| `self.current_order` / `plan_order_id` / `step_i` | 不再需要（Planner 为步进函数，靠 claims 关联订单） |
| `self.sub`（三套状态机共享） | 删除。顺序由 BT `Sequence` 承载（§7.1） |

## 5. Arbiter（仲裁层）

**定位**：每拍第一个跑。决定这拍把控制权交给哪个模式。**不执行任何动作。**

### 5.1 模式表

**`Stuck` 是前置守卫，不是优先级表里的一行。** 先说这条，因为它改变了表的读法：

```
if 卡住检测成立:          ← 跨模式生效，先于一切
      → Stuck 处理（保留原模式，脱困后原路返回）
else:
      → 按下表选模式
```

原因是死锁：若 `Firefighting`（优先级 1）高于 `Stuck`（优先级 2），那么**着火时被 P1 堵住就永久卡死**——`Stuck` 永远拿不到控制权，灭火树因走不到而反复超时重建。把脱困提为跨模式守卫即可解除：火中被堵 → 先脱困 → 继续灭火。

| 优先级 | 模式 | 进入条件 | 退出条件 | 执行 |
|---|---|---|---|---|
| 1 | `Firefighting` | **存在未被处理的着火灶 且 存在我可获得的灭火器** | **无未被处理的着火灶** | 灭火 task 树 |
| 2 | `Assigned` | `intents.assignments` 有未完成指派 | 指派完成 / 撤销 / TTL 到期 | 指派对应 task |
| 3 | `Normal` | 默认 | — | **交给 Planner** |

`Firefighting` 的条件改成了**资源视角**，而非初版的"有火 且 P1 没在灭"。初版有三个缺陷：

- **进入 / 退出不对称**：进入要求"P1 没在灭"，退出只看"火灭"。AI 进入后若 P1 也来灭，AI 会一直陪着（进入条件已不成立，但退出条件未满足）。
- **多火源歧义**：`onFire` 是哪个灶？多灶同时着火时退出条件无法判定。
- **多灭火器误判**：有两把灭火器时，"P1 没在灭"不该阻止 AI 参与。

改为"未被处理的着火灶"后三个问题同时消失：P1 正在灭的灶算**已被处理**，故不计入；只要还有没人管的着火灶且我拿得到灭火器，就该上。

**中断 task 的失败降级**：中断 task 连续 FAILURE 达 `N` 次 → 强制退回 `Normal`，并把该目标（这个灶 / 这把灭火器）拉黑一段时间。否则非 Normal 模式会反复重建同一棵必然失败的树，形成活锁。

### 5.2 模式的判据

**模式存在的唯一理由是"正常规划在此刻失效或不可能"**，而非"这件事很急"。按此判据：

- `Firefighting` —— 厨房在烧，做任何别的事都是白做，规划失效。**是模式。**
- `Stuck` —— 物理上执行不了任何计划，执行层故障。**是模式。**
- `Assigned` —— 用户显式指令主动覆盖规划。**是模式。**
- 丢弃烧糊、抢收熟料、锅找回 —— 规划完全有效，它们只是高分 task。**不是模式**，全部下放 Normal。

这把尺子推出一个重要结论：**整条锅的生命周期只有最后一格是模式。**

| 锅状态 | 该做什么 | 是模式吗 |
|---|---|---|
| `isCooking` | 不用管 | 否 |
| `cooked` | 取出装盘 / 端离灶台 | **否** —— task，分数随"快糊了"上升 |
| `burning` | 丢弃清锅 | **否** —— task，分数随"快着火了"上升 |
| `onFire` | 灭火 | **是** —— 模式 |

紧急度是一条连续上升的分数曲线，只有烧起来那一刻才升级为模式。这修正了今天"抢收熟料"作为行为树第 4 优先级分支导致的僵硬行为——会宁可丢下手里快送完的菜也要去抢收。

### 5.3 火情时 P1 已拿走灭火器

`Firefighting` 的进入条件包含"我能出上力"。若 P1 持唯一灭火器，AI **退回 Normal 继续产出**——P1 已在处理火，规划并未失效，两人围着一把灭火器才是浪费。

但 Normal 模式下**火的存在必须影响规划**（可行性约束，不是模式）：着火的锅不放料、不规划依赖它的 task、路径避开。

边界：P1 持灭火器但不灭火（没注意到 / 走开）。AI 客观无解，退回 Normal 继续产出并打日志。**这是对话层最有价值的场景之一**（未来可提示"锅着火了，灭火器在你手上"），本轮不实现。

### 5.4 两条转移纪律

1. **转移只能由 Arbiter 做。** 任何 task 树内部不许改模式。今天 `fire_branch` 闭包直接写 `self.mode` 是病根，新架构结构上不可能。
2. **转移时 halt 并丢弃当前 task 树**（松键，不保留进度 —— 见 §7.6），**丢弃上一模式的 scratch 对象**。

**模式有粘性**：退出条件必须真的满足才退，不因单帧信号抖动跳回 Normal（例：要 `onFire` 确实为 false 才退出灭火，避免火没灭完就跑）。

**可观测性**：每次转移打一行带原因的日志 `[mode] Normal→Firefighting (cooker#2 onFire)`。今天模式切换的原因藏在副作用里，日志看不出为什么。

**单测**：`(world, bb) → mode` 纯函数，可脱机断言。

## 6. Planner（规划层）

**定位**：无副作用的步进函数

```
plan(world, bb) → (chosen_task, claims', decision_record)
```

不持有可变状态、不发按键、不碰控制器；**返回**新认领状态由主循环写回。

**措辞纠正**：设计稿初版称 Planner"无状态纯函数"。类型上它确实无副作用，但**它的输出依赖自己上一拍写下的 claims 与 commitment**——它是一个有状态系统的纯步进函数，不是无状态规划器。这个区别对测试有实际后果，见 §6.6。

返回值里的 `decision_record` 是第三项新增：§8.3 的决策日志要求输出**全部候选的分数与 terms 拆解**，主循环拿不到这些，故必须由 Planner 一并返回。

五步流水线：**① 候选生成 → ② 可行性过滤 → ③ 协作过滤 → ④ 打分 → ⑤ 承诺惯性**

### 6.0 task 身份与候选生成

设计稿初版只写了"候选生成"四个字没有展开，而日志样例里却是 `FetchToPlate(Cucumber, plate3)` 这样的参数化实例——这个缺口会直接导致歧义，所以先定义清楚。

**task 实例 = `(type, order_id, bound_resources, bound_item)`**

两个 task 只有四项全同才是同一个 task。`FetchToPlate(Cucumber→plate_A, order#1)` 与 `FetchToPlate(Cucumber→plate_B, order#2)` 是**两个不同的 task**。

**为什么必须这样定义**（否则会出真 bug）：两单都缺黄瓜时，若 `FetchToPlate` 的完成判定不绑定具体盘，那么 **P1 把黄瓜放进盘 B，会让 AI 针对盘 A 的 task 误报 SUCCESS**——AI 以为自己干完了，盘 A 其实还空着。§6.1 表格里所有谓词都必须理解为**绑定参数上的函数**，而非全局谓词。

**枚举方式：从需求反向展开，不对资源做笛卡尔积。**

```
for order in 订单表:
    for 未满足需求 in diff(order.recipe, 该单已就位盘的 contents):
        候选 += 能推进该需求的 task（绑定具体资源）
+ 全局异常清理 task（StashHeld / RecoverLoosePot / Discard，与订单无关）
```

反向展开天然剪枝：已满足的需求不生成候选。候选数量级约为 `订单数(≤4) × 未满足需求数(≤4) × 可用资源数(≤3)`，**上限约 50**，每拍打分 50 次是毫秒级。配合 §6.4 的一次性 flood-fill（ETA 查表 O(1)），无性能问题。

**无 `order_id` 的 task 怎么算订单价值**：`StashHeld` / `RecoverLoosePot` / `Idle` 这三类与订单无关，打分时订单价值项记 0，只参与"解锁资源"与"时间压力"两项。

task 粒度 = **厨师的一趟差事**。边界切在"世界状态可明确观测"的地方——例如倒完饭后"手持空锅"是状态里直接读得到的事实，所以放回灶台切成独立 task，中断后看一眼手里就知道该干啥。

几个设计点：

- **第 5、12 号的可行性是纯观测事实**（"手持空锅" / "地上有锅"），不依赖任何记忆。这是火情丢锅能自动回收的机制——`AI_REVIEW.md` §4 那套专门的 `RecoverPotAction` 恢复逻辑和 `dropped_cooked_pot` 全局 bool **都不再需要**。
- **第 6 号 `RescueCooked`**：熟料在锅里同时是**资产**（现成食材，寿司关复用率极高）和**负债**（`cooked→burning→onFire` 计时在跑）。已确认的游戏机制：**把锅从灶台端起即停止烧糊，不必倒进盘子**。所以本 task 成本极低——端起锅放到就近台面，同时停计时、腾灶台、留料备用。
- **第 4 号可行性已放宽**为"存在缺此料的盘"而非"**我这单**需要"，自然包含 P1 那单的盘，接力协助免费获得。但须过第 ③ 步协作过滤：接力模式下倒进 P1 的盘是帮忙，**分单模式下不该碰他的盘**。
- **第 10 号完成判定用双信号**（订单消失 **或** 分数增加），因为人类可能同时送餐，单看订单消失会误判。
- **第 13 号 `StashHeld`** 是兜底：手里莫名拿着无用物（误拾、订单被抢后剩的料），清空手好继续干活。**但"随便放下"是不够的**，落点必须满足约束，见下。
- **第 14 号 `ResetPlate` 是新增的必要能力**（初版遗漏）。两个场景会楔死拼装格：① 盘里被放错料 → 对账只"失效认领"，那只错料盘仍停在拼装格上，`PlaceCleanPlate` 于是去放**另一只**盘，几轮后无格可用；② AI 端着料齐的盘走向出餐口时订单过期 → 承诺被弃 → 手里一只满盘。没有这个 task，上述两种状态无法恢复。
- **第 2 号 `WashPlate` 的取盘位置**：洗完的盘从**晾干架**出来，不是盘堆。`task.py:112` 已把 `t=="plate_return"` 且名字含 `drying` 的站点算作可取盘位（实测帧确有 `{'t':'plate_return','n':'DryingPart'}`）。初版完成判定只写"出现可用干净盘"没说去哪取，实施时会漏。
- **第 11 号 `Discard` 必须去垃圾桶**。烧焦的锅内容**只能倒进垃圾桶**才能清空，不是随便放下。现有 `_discard_tick`（`agent.py:852`）有完整流程（找 bin → 走过去 → 倒掉 → 取回锅），`task.find_station(w,"bin",...)` 是真实站点。故 `Discard` 的认领含垃圾桶。
- **上下游咬合**：每个 task 的"完成判定"即下游 task 的"可行性"（1 的完成 = 4/9 的可行；4 的完成 = 5 的可行）。同一谓词写一份两处用，前后校验口径天然一致。**前提是谓词按 §6.0 的绑定参数求值**，否则多订单下咬合不成立。
- **`Idle` 不在候选集里**。初版把 `Idle` 的可行性写成"无其他可行 task"——这不是世界谓词，而是对候选集本身的谓词，与"每个 task 自己声明是否可做"的原则冲突。改为：`Idle` 是流水线第 ⑤ 步之后的 **fallback**，不参与打分。`Prefetch` 则保留在候选集中并给了真正的世界谓词（见表格第 15 行）。

> ⚠️ **修正（写 Plan 2 时在 801 真实帧上发现）**：上表第 4、9、10 号的完成判定写"盘 `contents` 含该料"，**按字面实现会死循环**。盘里的料名与订单需求名是两套词汇：
>
> | 订单 `composition` | 盘 `contents` 实际写的 |
> |---|---|
> | `BoiledSushiRice`（熟料） | `CookedCompositeAssembledNode`（不透明 token） |
> | `SushiFish`（需切，板上是 `ChoppedSushiFish`） | `SushiFish`（**生料名**，不是切后名） |
> | `Seaweed`（直接放） | `Seaweed` |
>
> 一张做完的 `Sushi_Fish` 盘是 `['CookedCompositeAssembledNode','SushiFish','Seaweed']`，三样里只有两样字面对得上。按字面比较则 `plate_lacks(plate,"BoiledSushiRice")` 恒为真 → 第 4 号的完成判定永不成立 → AI 把饭倒进盘后以为没倒，无限重倒。
>
> **修法**：加一层装盘态词汇映射（`RecipeBook.plate_token`），三条规则——需烹饪的料 → 不透明 token；需切的料 → 生料名；其余 → 原名。详见 Plan 2 的 Review Focus 第 0 条与 Task 5。
>
> **已知局限**：熟料 token 不透明，故同一盘需要两份不同熟料的菜（如 `Pasta_Marinara_New` 要 `BoiledPasta` + `PanFriedPrawns` + `PanFriedFish`）无法区分。本轮目标关卡 Sushi_1_4 每道菜只有一份熟料，不受影响；多熟料菜需靠 `count` 计数或插件补字段，归 Plan 3 的已知缺口。

**手持状态必须纳入可行性**（初版遗漏，会直接出错）。除第 5 号（手持空锅）和第 13 号（手持无关物）外，初版其余 task 的可行性都不提手里有什么。后果：手持盘子时 `FetchToCooker` 判为可行，其树首 `InteractWith(crate, pickup)` 会失败或触发物品交换。

两种解法，**本设计选 (b)**：

- (a) 所有需空手的 task 树首强制 `EnsureHandsFree` —— 省事，但放弃了"先把盘用完再腾手"这类更优解。
- (b) **把手持状态纳入可行性，并给"需腾手"加一个 ETA 惩罚项** —— 这样打分才能正确比较"先放下盘再去拿料"与"先把盘用完"。

具体规则：task 声明自己需要的手部前置（`空手` / `持盘` / `持锅` / `任意`）。不满足时**不是不可行**，而是在 ETA 上加腾手代价（约 `EnsureHandsFree` 的步数）。只有腾手本身不可能时（如手持物无处可放）才判不可行。

**落点约束（`StashHeld` / `RescueCooked` 共用）**：现有 `_find_drop_cell`（`agent.py:483`）的筛选逻辑是**功能性的、不是优化**，必须保留——落点须可落脚、非传送带，且不贴灶台（会继续加热）、不贴出餐口（会被误上菜）、不贴拼装台（会挡盘）。初版只写"清空手"会丢掉这些约束。

### 6.2 可行性过滤 —— 最关键的设计决定

**不建显式 DAG、不做拓扑排序。每个 task 自己声明"此刻我是否可做"（一个世界谓词），执行顺序从可行性中自然涌现。**

- 饭没熟 → `TakeCookedToPlate` 自动不在候选里。
- 盘没就位 → `FetchToPlate` 不可行。
- 料没齐 → `DeliverPlate` 不可行。

因此**不需要记录"我做到第几步"**。无状态重算、中断自愈、用户抢单自适应，全部源于这一点。今天 `task.py` 的 `decompose()` 输出线性步骤序列，正是这里要换掉的东西。

火情中的锅、P1 手里的那块料、不可达的站点，都在这一步判为不可行。

### 6.3 协作过滤 —— 两种协作模式

两种模式共用同一套 task 生成 / 打分 / 执行，**区别只是打分前的一道筛**：

| 模式 | 开关 | 分法 | 实现 |
|---|---|---|---|
| **接力 / 流水线** | `--collab=relay`（默认） | 同一道菜按步骤分 | 不筛，只对 `p1_active_task` 做分数惩罚 |
| **分单** | `--collab=split`（默认关闭） | 一人一道菜 | 只留 `order_assignment == "P2"` 的 task |

**"分工位 / 角色"已从模式降级为对话层意图**（初版把它列为第三种模式是设计错误）。原因：它与另两者性质不同——接力 / 分单是 AI 需要**自己推断**的协作规则，而分工位来源只能是用户的一句话（"你管锅我管切"）。而"看几拍行为"根本无法区分"他在切菜"和"他负责切菜"，所以让 AI 推断分工位注定是摆设。

它的正确落点是 `intents.role_constraint`：用户说 → 解析 → 写黑板 → 协作过滤加一道**task 类型筛**。复用已有注入口，不需要新机制。

**由此得到一条设计原则**：**用户能一句话说清的约束，走意图注入口；只有 AI 必须自行推断的，才配得上一个模式。**

**分单模式默认关闭的理由**：它的死锁 / livelock 只在"双方同时争抢特定资源"时出现，而这需要人类配合才能复现——正是验证最薄的环节。故机制完整实现（§4.3 的 waiters / 超时让出 / §6.3 的归属分配），但默认不启用：主路径（接力）不承担它的风险，出问题关掉开关即可，无需回滚。配合 §11 的**录帧回放测试台**，分单的死锁场景可离线构造——这是唯一能把它验透的手段。

#### 接力模式：避让与追求

要避的三件事：

1. **抢同一个具体物件**（P1 正伸手去拿的那块黄瓜）。
2. **重复劳动**（同一订单的同一料位，他切了我不切）。
3. **站位打架** —— 归属明确为 **World 层**：按 `p1_model` 产出一张**软代价图**（P1 周边格子加通行代价），由 flood-fill 统一消费，于是所有 ETA 自动绕开 P1 周边。不放在 Planner 或 Executor（`MarkBlocked` 是脱困专用）。

反过来要**主动追求接力**：他煮饭我取饭、他切菜我装盘、他装盘我送餐。接力 task 在打分中加成。

**`p1_active_task` 是分数惩罚，不是硬否决**（初版写成硬 veto，是个会导致 livelock 的错误）。硬 veto 的问题：一旦推断错（P1 拿着黄瓜走开了），该动作被**无限期**排除，AI 会一直等 P1 做一件他根本不做的事。而黑板里明明有 `confidence` 却没用上。

规则改为：

- `p1_active_task` 按 `confidence` 缩放为**分数惩罚**，置信度越高惩罚越重。
- 硬 veto 只保留给**物理争抢同一具体物件**的情形（上面第 1 条）。
- `p1_active_task` 带 TTL：无新证据则 `confidence` 衰减至 0，推断自动失效。

**两人同时想做同一 task** 的三层兜底，不需要复杂协商：ETA 比较（谁更近就让）→ 承诺惯性（不每拍改主意）→ 真撞上了由后置校验发现"饭已不在锅里"→ task FAILURE → 重算。

#### 分单模式：三条规则

- **订单归属**：新订单到达时按双方当前负载分配（各自在手 task 数 + 已认领资源数），写入 `bb.order_assignment` 并**持久化**——不每拍重算，否则归属会抖。
- **归属为空即退回接力**：若无任何订单归属 AI（分配尚未发生、或推断有误），**立刻退回接力模式**。这是必须的保护：否则一次推断错误就能让 AI 在明明有活干时站着不动——最糟的失效形态。初版只覆盖了"我的单做完"这一种情况。
- **资源争抢**：走 §4.3 的 waiters 队列 + 超时让出，不永久避开也不死等。

**取舍**：在锅 / 板稀缺的关卡（如 Sushi_1_4）**接力通常效率更高**（专业化分工、少跑路、资源串行利用）；分单在站点成对的关卡才占优，但对人类**更好理解**（"这单归我"心智负担低）。故两者都实现、默认接力、一句话可切换。

### 6.4 打分

六项加权：

| 项 | 含义 |
|---|---|
| 订单价值 / 紧迫 | 订单分数、`remaining`、combo |
| **时间压力曲线** | `cooked → burning` 分数持续上升，避免被饿死 |
| **异步资源优先** ⭐ | **下锅这类"启动后自己跑"的 task 加重分** |
| ETA | flood-fill 路径代价，近的便宜的优先 |
| 接力加成 | 承接 P1 上游的下游 task |
| 完成度 | 快装齐的盘优先推完，别留半成品 |
| **料复用 / 批量** ⭐ | 该次取料同时满足 ≥2 单的需求则加成（初版漏项） |
| **combo 延续** | 与上一次出餐同菜则加成（combo 依赖连续出同类菜） |
| **截止前瞻** ⭐ | 启动后会错过已知截止（锅烧糊时刻、订单到期）则惩罚 |

**"异步资源优先"是 Overcooked 效率的命门**：煮饭要约 20 秒，越早启动越能与自己的劳动并行。这一项让 AI 自动学会"先把饭下锅，趁煮的 20 秒去切下一单的菜"——**穿插是打分涌现的，不写死顺序**。

另：若救出熟料顺带解锁了我这单要用的锅，该 task 加成（同时完成"救料"和"腾资源"）。

**后三项是初版的缺口，必须补**：

- **料复用 / combo**：§1 把"料复用"和"合并同类采购"列为能力，但初版六项里没有对应项，combo 也只是在"订单价值"里出现了一个词。而 combo 本质是**序列性质**（连续送出同类菜），单 task 贪心打分表达不了，必须单列一项。
- **截止前瞻**：初版的 ETA 是**到达成本**，不是 task 的**执行时长**。但"这 20 秒够不够我去切下一单的菜并回来取饭"恰恰需要时长。故给每个 task 类型加粗粒度 `est_ticks`（常量 + ETA），并在打分中惩罚"会错过已知截止"的选择。**这是四项能力里唯一需要前瞻的部分，纯贪心无法涌现。**

**权重分批上线**（约 9 个互相作用的旋钮，一次全开无法调参）：初版只启用 **订单紧迫 / 时间压力 / ETA** 三项跑通，其余按 §11.4 的回放证据逐项加入，每加一项记录一次基线。

### 6.5 承诺惯性（防抖）

选中 task 登记进 `commitment`，之后**除非完成 / 失败 / 连续 M 拍不可行 / 出现分数显著更高者（超过 margin + 进度加成）**，否则不改选。

**算得勤是好事，改主意勤才是坏事**：每拍重算带来响应性（火情、P1 抢单、物品掉落下一拍即反应），承诺惯性保证行为稳定。两者不矛盾。

两条额外规则，**各自修掉一个真实缺陷**：

**(a) 进度 / 沉没成本项 —— 否则会复活 §5.2 声称已修掉的毛病。**

初版的"时间压力分数单调上升"配"超过固定 margin 就改选"，意味着烧糊临界那一刻 `RescueCooked` 的分数**必然穿透任何固定 margin**——AI 会在离出餐口两格时放下盘子跑去端锅。这个行为与旧架构完全等同，只是从树的优先级搬到了打分里。

修法：改选门槛随当前承诺的完成度上升（`steps_done / est_steps`），即"剩余步数少"的 task 获得固定加成。离出餐口一步时，任何中断都得非常值钱才抢得动。

**(b) 不可行需连续 M 拍成立才弃。**

初版规定"变不可行即弃"，但 20 Hz 下一帧抖动（P1 手臂短暂挡住料、快照延迟、物品搬运中的瞬时缺失）就会让当前承诺瞬时不可行而被丢弃。§5.4 给了**模式**粘性，却没给**承诺**粘性。故用 `commitment.infeasible_streak` 计数，连续 M 拍不可行才放弃。

两条都配场景单测（见 §11.3）：「离出餐口一步时另一锅进入 burning」断言**不改主意**；「料被 P1 挡住一帧」断言**不弃**。

**ETA 的计算优化**：每拍从厨师位置做**一次 flood-fill BFS** 得到到所有格的距离表，所有候选 ETA 查表 O(1)。每拍 1 次 BFS 替代 N 次（N≈10-20），并被脱困、可达性判断复用。今天 `world._bfs` 是 start→goals 定向搜索，新增全图变体。

不做"仅变化时重算"的增量优化：过早优化，且引入漏检风险。

**无 task 可做时**：预取常用料或走到中立位待命，而非站着不动。

### 6.6 可测试性

Planner 无副作用，这是本次重设最大的工程红利。给一帧假 World + 假黑板，断言"选中了预期 task"。可构造"饭熟了同时快送完餐""订单被人类抢走""两人同时想取同一锅"等场景，**脱离游戏验证决策是否聪明**——今天这类验证只能实机碰运气复现。

**但构造 fixture 有个陷阱**：Planner 的输出依赖自己上一拍写下的 claims，所以测试要构造一个**自洽的黑板历史**，否则测到的是不可能发生的状态。因此需明确黑板不变式，至少包括：

- 认领的资源必须在世界中存在；
- `claims` 的 `order_id` 必须在当前订单表中（除非正在被对账清理）；
- `commitment.active_task` 所需的认领必须由自己持有；
- 同一 `(resource, action)` 不能有两个 owner。

提供一个 `make_bb(...)` 辅助构造器，自动维持上述不变式，避免每个测试手搓黑板。

### 6.7 P1Model（人类意图推断）

初版只给了一个模块名，推断算法仅一句话，且 §11 还引用了一个文中不存在的"三层推断"——这一节补齐。

**定位**：推断的是**人类玩家 P1 在做什么**，目的只有一个：让 Planner 避开撞车、接管下游。AI 自己（P2）的意图不需要推断，它写在 claims 里。

**可用信息比想象的多**：状态协议里 P1 与 P2 **完全对称**（`chefs[]` 两者字段相同：`name` / `x` / `z` / `yaw` / `held` / `interactions`）。所以"看" P1 和"看"自己一样全——手持、位置、朝向、正在交互的站点都读得到。这不是黑箱猜测，是**从可观测行为做短程推断**。

**三层输出**（置信度递减）：

| 层 | 内容 | 来源 | 置信度 |
|---|---|---|---|
| **1. 事实** | `holding`（手持何物）、当前交互站点 | 直接读 `chefs[P1]` | 1.0（不是推断） |
| **2. 短程意图** | `p1_active_task`（他正在做哪个动作） | 手持 + 位置 + 朝向 + 最近交互格 | 0 ~ 1，见下 |
| **3. 显式告知** | `intents.assignments` / `role_constraint` | 对话层（本轮预留） | 覆盖第 2 层 |

**第 2 层的推断规则与 confidence 定义**：

- 正在交互某站点 → `confidence = 1.0`（观测到的事实，不是预测）。
- 手持 X 且朝目标站点移动中 → 推断"他要把 X 送去该站点"，`confidence ≈ 0.7`。
- 手持 X 但静止 / 朝向不明 → **不推断动作**，只登记第 1 层事实（占用 X），`confidence = 0`。
- **衰减**：每拍无新证据则 `confidence *= DECAY`；低于阈值即清空 `p1_active_task`。`last_evidence_tick` 记录最近一次支持证据的拍号。

**宁可不推**：置信度低时只登记事实、不预测动作。配合 §6.3 的"惩罚而非硬 veto"，推断错误的代价被限制为"分数略有偏差"，而不是"AI 僵住等一件不会发生的事"。

**优先级**：显式指令（第 3 层）永远覆盖推断（第 2 层）。P1Model 提供的是"没有明确指令时的默认协同"。

**验证**（解决初版"阶段 6 不可回归"的问题）：录制人类对局的原始帧，建**回放测试台**——把录制帧喂给 P1Model + Planner，断言推断结果与协作决策。这是唯一能让 P1 协同具备离线门槛与回归网的手段。

**核心取舍**：用"可行性谓词 + 打分"替代"显式步骤序列"。代价是决策不如写死顺序那样可预言（须看打分），收益是中断自愈、动态改单、多订单穿插全部免费且可单测。打分权重需实机调参，初始权重与调参方法见 §11。决策可观测性（§8）是这一取舍的配套解药。

## 7. Executor（执行层）

**定位**：把 Planner 选中的一个 task 变成这一拍的按键。用现有 `bt.py`，但**叶子只能是带强制校验的原语**。

### 7.1 关键发现：今天的 actions.py 在重复发明 Sequence

今天每个动作类内部手搓一个字符串子状态机（`sub = "goto_from" → "confirm_from" → "goto_to" → ...`），而 `bt.py` 的 `Sequence` **本来就是干这个的**。747 行里大量代码是在手工实现"按顺序推进 + 记住推到哪"，引擎已免费提供。

因此：**task 树 = Sequence 串起来的原语，`self.sub` 字符串状态机整体删除**，顺序状态由 BT 的 RUNNING / halt 机制承载（`AI_REVIEW.md` Bug#2 时加的 `halt()` 正好派上用场）。

### 7.2 原语库

**核心交互**

| 原语 | 职责 | 强制校验 |
|---|---|---|
| `Approach(target, kind)` | 走到交互位 | **前置**：`placement_gx/gz` 或 `pickup_gx/gz` 匹配目标才算到位；不可达 → FAILURE。**只保证站位，不保证朝向** |
| `Face(target)` | 转向目标 | 朝向正确 |
| `Tap(key, hold)` | 单击（`hold` 覆盖倒料 / 切菜的按压时长） | **去抖**：见下 |
| `TapWhileHolding(tap_key, hold_key)` | 按住 `hold_key` 的同时单击 `tap_key` | 传送带顶位专用，见下 |
| `HoldUntil(key, pred, timeout)` | 按住到条件成立：切菜 / 喷灭火器 / 洗盘 | 超时 → FAILURE。**`timeout` 无默认值，必须显式传** |
| `Confirm(pred, retries)` | 校验世界真的变了 | **后置**：不满足则有限重试，仍不行 → FAILURE |
| `Settle(ticks)` | 等状态刷新 / 物理稳定 | — |
| `EnsureHandsFree` | 手里有东西就放到就近合法台面（落点须满足 §6.1 的落点约束） | 后置：手空。**幂等**——手已空直接 SUCCESS，故可无条件置于任何树首 |
| **`InteractWith(target, kind, expect)`** | **= Approach + (Face) + Tap + Confirm** | 前置 + 后置齐备 |

**`Face` 与 `Approach` 的分工**（初版两处自相矛盾，此处定稿）：`Approach` **只管站位**，`Face` 单独负责朝向。因此所有需要定向交互的地方都必须显式带 `Face`，包括 `InteractWith` 的内部展开。灭火必须面朝火源才喷得到——今天 `_fire_tick` 有专门的 `face_fire` 子状态 + `face_ticks` 计数，证明这是真实需求。

**`Tap` 必须去抖（初版遗漏，会直接出 bug）**。`agent.py:921` 的注释明写「拾取是 toggle，连点会拿起又放下」。而新设计是每拍重算 + 20 Hz 循环，若 `Tap` 无保护，同一个 `InteractWith` 在相邻几拍会重复按键，表现为**反复拿起放下**。规则：

- `Tap` 为**边沿触发**：同一节点实例在一次激活期内只按一次，按完进入 `Confirm` 等待世界变化。
- 重试由 `Confirm(retries)` 显式控制，而不是靠反复 tick 自然重按。
- 同一按键的两次 `Tap` 之间强制最小间隔（`TAP_COOLDOWN_TICKS`）。

**`TapWhileHolding` 是传送带的必需能力（初版完全遗漏）**。在传送带格上拾取时，必须**同时按住反向键顶住**，否则角色会被传送带推走。现有 `_grab_burst`（`agent.py:920`）+ `_belt_counter`（`agent.py:947`，计算反向键）就是干这个的，而本关 `Sushi_1_4_2P` 有传送带——这是实跑踩出来的坑，不是理论问题。初版的 `Tap(key, hold)` 两参数表达不了"按住 A 的同时点 B"，故单列一个原语。

**脱困专用**

现有脱困是**分级**的，三级都要保留（初版只覆盖了 L1 / L2）：

| 级别 | 触发 | 处理 | 新设计落点 |
|---|---|---|---|
| **L0** | 刚脱困完 | 松键停等 `RECOVER_TICKS` 拍，**本拍不做任何决策** | `StuckScratch.skip_ticks`，由主循环第 ⓪ 步短路（见 §8.1） |
| **L1** | 首次卡住 | 把卡住的格拉黑（TTL） | `MarkBlocked(cell, ttl)` |
| **L2** | 同一格卡 2 次 | 侧向微移 | `Nudge(dir, ticks)` |
| **L3** | 同一格卡 ≥3 次 | **放弃当前目标、整体重规划** | `AbandonTarget(target, ttl)`：拉黑**目标**（非格子）并强制 commitment 失效 |

| 原语 | 用途 |
|---|---|
| `Nudge(dir, ticks)` | 侧向微移（L2） |
| `MarkBlocked(cell, ttl)` | 把卡住的格拉黑写入 `scratch.StuckScratch`（执行层对该字段有写权，规则一致）（L1） |
| `AbandonTarget(target, ttl)` | 放弃该目标并拉黑一段时间，触发重规划（L3） |

**L3 不能用 `Timeout` 替代**：`Timeout` 的触发条件是"耗时过久"，L3 的触发条件是"**同一格反复卡**"（`last_cell` / `same_count` 计数）。一个 task 可能反复卡在同一格但每次都没超时，Timeout 永远不响。两个机制都要有。

**结构性安全网**

| 机制 | 说明 |
|---|---|
| `Timeout(task, max_ticks)` 装饰 | **整个 task 级超时**。今天只有单步重试，没有"这个 task 卡了 30 拍"的兜底。任何 task 异常久 → FAILURE → Planner 重算。防死循环的最后一道闸 |

合计 **11 个原语**（核心交互 8 + 脱困 3）**+ 1 个复合（`InteractWith`）+ 1 个超时装饰**。`InteractWith` 这一个复合原语替代今天约 **22 处**逐字复制的 "goto → tap → confirm" 模板（实测：`confirm*` 子状态分支 22 个、`_goto*` 调用点 22 个、`confirm_wait < 2` 重试样板 17 处）。

### 7.3 task 树的样子

```
FetchToBoard(Cucumber, board) = Sequence[
    InteractWith(crate, pickup,    expect = held(Cucumber)),
    InteractWith(board, placement, expect = board.item == Cucumber),
]

Chop(board) = Sequence[
    Approach(board),
    Face(board),                                          ← 朝向不由 Approach 保证
    HoldUntil("chop", board.item == 配方期望加工态, timeout=CHOP_TIMEOUT),
]

Firefighting = Sequence[
    EnsureHandsFree,                                      ← 优雅退出在此解决
    InteractWith(extinguisher, pickup, expect = held(ext)),
    Approach(burning_cooker),
    Face(burning_cooker),
    HoldUntil("chop", not cooker.onFire, timeout=FIRE_TIMEOUT),
]

# 传送带上取料：必须顶住反向键，否则被推走
FetchFromBelt(item, belt) = Sequence[
    Approach(belt, pickup),
    TapWhileHolding(tap_key="pickup", hold_key=belt.counter_dir),
    Confirm(held(item), retries=2),
]
```

**`Chop` 的完成判定不用字符串前缀匹配**。初版写 `item == Chopped*`，但多阶段切配（需切两轮）或产物命名不以 `Chopped` 开头时会误判。改为"板上产物 == **配方期望的加工态**"，由 `predicates.py` 从配方数据（`crate.chop` / `chop_stages`）取——这与 §9 "配方数据驱动"的方向一致。

今天 97 行的 `MoveAction` → 两行声明。且校验**写不掉**：`InteractWith` 的构造要求必须给 `expect`，没有后置校验就建不出节点。**这把"验证优先"从口号变成结构强制。**

### 7.4 优雅退出：中断时手里拿着东西

场景：角色拿着黄瓜要去切菜板，火情出现，必须先放下黄瓜才能拿起灭火器。

今天的 `halt()` 只做"松键"，是急刹车而非优雅退场——这正是 `AI_REVIEW.md` §4 那个坑（去拿灭火器的 `pickup` 把手里的锅丢地上，火灭后找不回）。

**设计决定：优雅退出由抢占方负责前置条件，而非被打断方负责清理。**

- 被打断的 task 树：`halt()` 只松键 + 清移动方向，然后**丢弃**（§7.6）。保持简单。
- 抢占方（中断 task）：**树的第一个节点是 `EnsureHandsFree`**，把手清空到就近合法空台面，再去拿灭火器。

理由：
- **职责清晰**。"灭火需要空手"是灭火的领域知识，写在灭火树里；切菜树不需要知道灭火的任何事。
- **复用**。`EnsureHandsFree` 被灭火、丢弃等多个中断共用。
- **halt 保持纯粹**，不碰物品，不必每棵树各写一套放置逻辑。

**放下的黄瓜不需要专门回收**：火灭后回 Normal，Planner 看当前世界"黄瓜在台面上、没切、盘里缺黄瓜"，自然重新规划。`task.find_ingredient` 已有 `kind:"loose"` 分支。**这就是无状态重算的红利——中断不需要"恢复"，只需要"重新看世界"。**

放置位置要讲究：放**就近的合法空台面**而非地上（地上虽也能捡，但可能挡路或在传送带上被冲走）。

### 7.5 执行可靠性：三类校验缺口

今天的校验不成体系：有的查 held 变化，有的只数拍数就往下走，还有残留固定延时（`_tick_wash` 用 `confirm_wait >= 20` 兜底，20 Hz 下约 1 秒）。新架构把"前置校验 → 动作 → 后置校验"做成**原语基类强制的结构**。

| 故障场景 | 由谁拦 | 怎么拦 |
|---|---|---|
| **放错格子**（目标 `(1,1)` 却放到 `(1,0)`） | `Approach` 前置 + `Face` | `Approach` 确认站在能作用到目标格的交互位（用 `placement_gx/gz`，`AGENTS.md` §6 称其为"能否交互的最精确信号"），`Face` 确认朝向。**前置不通过，动作根本不执行** |
| **放下失败**（按了但没放成） | `Confirm` 后置 | **双条件**：手里东西没了 **且** 目标位置真的出现了它。只查"手空了"不够（可能掉地上）。今天 `held_before` 字段名存实亡，是漏洞 |
| **误放下 / 误拾**（没打算放却放了） | 手部连续性不变式 | 每个原语开头确认"手里的东西与我以为的一致"，不一致说明中间发生意外 → 停下来让 Planner 按现实重算 |

**核心思路**：不追求"永不误操作"（物理键盘注入做不到 100%），而追求"**误操作后下一拍必被检测到并自愈**"。

**现有 `settle_*` 稳定拍被 `placement_gx/gz` 前置校验取代 —— 这里显式记一笔，否则实施时会丢。** 今天 `actions.py:100` 的 `settle_counter` 和 `314` 的 `settle_to` 是"走到位后等一拍再按键"的缓冲，防止滑行中按键落空。新设计不需要它：`Approach` 的前置校验直接读 `placement_gx/gz`，这是**比等待更可靠的判据**（等一拍是赌物理稳定了，查交互格是确认真的能作用到目标）。`Settle` 原语仍保留，但只用于等**状态刷新**（如倒料后等 contents 更新），不再用于等物理稳定。

### 7.6 三条执行纪律

1. **失败一律交还 Planner**。任何原语 FAILURE → task FAILURE → 下一拍 Planner 按现实重算。**Executor 不写任何恢复逻辑。** 上述所有意外都走这一条路，不需各写专门兜底。校验负责**发现偏差**，无状态重算负责**从偏差中恢复**。
2. **halt 只松键，并丢弃树**。手里的东西交给抢占方的 `EnsureHandsFree`。
3. **不碰 claims**。执行层不做资源分配决策，只读黑板。

#### 树的生命周期（修正一处结构性矛盾）

设计稿初版三处都写"halt 保留 BT 进度以便续跑"，但这与"Planner 每拍返回 task、不记录做到第几步"**无法同时成立**——而且黑板字段里根本没有存放树实例的地方，按初版实施，每拍新建的树进度恒为零，"保留进度"是空话。

**定稿规则**：

| 事件 | 树的处理 |
|---|---|
| task 身份与上拍相同 | **复用同一棵树**（进度自然保留，这是常态） |
| task 身份变化 | 丢弃旧树（先 `halt`），按新 task 构建 |
| 被中断模式抢占 | `halt` 并**丢弃** |
| 中断结束回 Normal | 重新构建（不恢复旧树） |

归属：树是 **Executor 持有的跨拍对象**（`executor.active_tree`），不进黑板——它不是需要被别层读取的状态。

**为什么"丢弃"的代价很小**：树只有 2-4 步线性结构，重建成本接近零；而中断后世界已变，续跑旧进度本身就不安全（§7.4 的"放下的黄瓜不需要回收"正是同一个道理——不恢复，只重新看世界）。初版想保留进度，其实是旧架构"动作自带 sub 以便续跑"思路的残留。

### 7.7 关于 bt.py：维持手写，顺手精简

重新评估（前提已变：引入了显式 Blackboard，py_trees 的主要迁移障碍消失）后仍维持手写，但理由不同于 `AI_REVIEW.md` §5：

1. **BT 职责大幅缩小。** 新架构里树只负责单个 task 的 2-4 步线性顺序——**这是第三方库价值最低的场景**。库的收益随树复杂度增长，我们的树正在往简单走。
2. **我们的 Blackboard 不是通用 KV store。** 它有 claims + 对账逻辑、P1 模型、意图口；py_trees 的 Blackboard 是带访问追踪的键值存储。接进去就得二选一：把结构塞进它的模型（丢控制权），或两个黑板并存（难看）。**这是决定性的。**
3. **项目零依赖**（`AGENTS.md`：仅标准库 + pyobjc，无 requirements / venv）。引包要付 Python 3.9.6 兼容与依赖管理成本，换来的可视化**恰好不是需要的那种**——需要看的是 Planner 打分表，没有 BT 库提供这个（见 §8）。

反向结论：`bt.py` 现在**超配**了。实际只需 `Sequence / Selector / Condition / Action / halt`；`Parallel` 从未接入（`AI_REVIEW.md` 优化项 1 自承"多厨师预留，未接入"）。**精简：删除 `Parallel`。**

`actions.py` 747 行 → `primitives.py`（约 150 行）+ `tasks.py`（约 100 行）。减少的主要是重复的状态机样板与确认模板。

## 8. 主循环、文件布局与决策可观测性

### 8.1 主循环（每拍十三步）

今天的 `decide()` 83 行做五件事（另有 `_build_tree()` 112 行），新主循环只做装配，逻辑全在各层：

```
① 收帧 → World
② 若 scratch.skip_ticks > 0  → 松键、递减、return     脱困 L0 短路（§7.2）
③ reconcile_claims(world, bb)        认领对账 + 四个释放触发点（§4.1）
④ p1model.update(world, bb)          更新 P1 推断与 confidence 衰减
⑤ stuck_guard(world, bb)             卡住检测：跨模式前置守卫（§5.1）
⑥ mode = arbiter.select(world, bb)   三行模式表
⑦ 模式变了 → halt 并丢弃树 + 丢弃上一模式 scratch
⑧ (task, claims', record) = planner.plan(...)   若 Normal，否则取该模式的中断 task
⑨ bb.claims = claims'                ★ 写回认领（初版漏了这步）
⑩ 登记 / 更新 commitment              ★ 记 steps_done、infeasible_streak（初版漏了这步）
⑪ executor.tick(task) → 按键
⑫ 处理 SUCCESS / FAILURE → 按 §4.1 推进或释放认领、清 commitment
⑬ trace.emit(record)                 决策记录 JSONL
```

★ 两步是修补：初版九步里**没有写回 claims、也没有登记 commitment**，而这两者是 Planner 的输出和承诺惯性的载体——不写回则认领与承诺永远为空，整个 §4 / §6.5 失效。

生命周期守卫（沿用今天）：暂停 / 非关卡 → `release_all`；socket 断 → 退出；`SIGINT` / `SIGTERM` → `release_all`。

**flood-fill 的位置**：在 ① 之后、⑧ 之前算一次（帧号未变可复用缓存），结果挂在 World 上供 Planner 的 ETA 查表。

### 8.3 决策可观测性

**为什么这是一等设计目标**：旧架构里行为树就是决策逻辑，看树=看决策。新架构里决策分散在三层：

| 层 | 决定什么 | 看 BT 能看到吗 |
|---|---|---|
| Arbiter | 当前哪个模式 | ✗ |
| **Planner** | **为什么选这个 task 而不是别的** | ✗ |
| Executor | 这个 task 执行到第几步 | ✓ |

**只做 BT 可视化只能看到最后一公里。** 真正需要看的是 Planner 的打分表。这也是 §6.6 那个取舍（打分涌现 vs 写死顺序）的配套解药。

**形式（已确认方案）**：每拍一条结构化 JSONL 写入 `/tmp/agent.log`，并把 `tree_viz.py` 扩成"读 JSONL 回放任意一拍"的查看器。零依赖，贴合既有 grep 回放习惯，可脱机重播。

未来若需实时 TUI 或 Web 面板，可在这份 JSONL 基础上叠加，不必返工。

**记录格式**：

```json
{"t":1283, "mode":"Normal", "mode_reason":"no fire",
 "p1":{"held":"Cucumber","active_task":"Chop(board2)"},
 "candidates":[
   {"task":"DeliverPlate(plate3)","score":9.1,"ok":true,
    "terms":{"order":4.2,"eta":-0.8,"progress":3.0},"chosen":true},
   {"task":"TakeCookedToPlate(cooker1)","score":8.4,"ok":true,"terms":{"...":0}},
   {"task":"FetchToCooker(Rice,cooker2)","ok":false,"veto":"p1_active"}],
 "commit":{"task":"DeliverPlate(plate3)","ticks":6},
 "exec":{"node":"Approach(window)","status":"running"},
 "keys":["right"]}
```

`terms` 把打分拆成各项，故日志能直接回答"为什么选它"；`veto` 记否决原因。

渲染成 ASCII 决策表的样子：

```
tick 1283  mode=Normal  (P1: chopping@board2)
候选 task                        分数   可行  说明
  TakeCookedToPlate(cooker1)     8.4   ✓    熟+盘就位+快糊了(+2.1)
→ DeliverPlate(plate3)           9.1   ✓    料齐+订单剩18s  ★选中
  FetchToBoard(Cucumber,board1)  5.2   ✓
  FetchToCooker(Rice,cooker2)     —    ✗    P1占用该动作
承诺: DeliverPlate(plate3) 已持续 6 拍
执行: Sequence[InteractWith(plate)✓ → Approach(window)▶ → Tap]
```

**体量控制**：5 Hz × 约 1.5 KB ≈ 36 MB/小时。默认只记**选中项 + 前 3 名的完整 `terms`**，其余仅记分数；`--trace-full` 开全量。

<details>
<summary>原（错误）推导——仅供追溯，<b>不要照此实现</b></summary>

设计稿初版猜测 `GRID_OZ == -origin.z`，**这是错的**。改猜 `mapOffset`：

```
GRID_OX =  size.x * mapOffset.X   =  1.2 * 8 =  14.4  ✓   ← 假：实算 = 9.6
GRID_OZ = -size.z * mapOffset.Y   = -1.2 * 6 =  -6.0  ✓   ← 假：实算 = -7.2
```

"61/61 零违例"验证的是 `x = 14.4 + 1.2*gx` 这条**线性关系**成立，**不是**它上面那条 `mapOffset` 推导式——中间那步算术从未被核验，把"线性拟合成立"误当成"推导式成立"了。

</details>

**实际方案：世界原点从站点自动校准。**

`mapOffset=(8,6)` 恰是 `nodeMap`（17×13）的**中心下标**，是个纯索引量，描述"网格原点落在 nodeMap 数组的哪一格"（`GetIndexFromPoint(p) => (p.X - mapOffset.X, p.Y - mapOffset.Y)`，`oc/AI_REVIEW.md:125`）。它**不含世界空间位置**，因此原则上无法推出世界原点——用它算 `node_index` 是对的（61/61 站点落点均为占用格），算 `origin_*` 是错的。

正确做法：从任一带 `gx/gz` 的站点反解

```
origin_x = x - cell * gx     origin_z = z - cell * gz
```

对实测帧 61 个站点逐个反解，结果**完全一致**（`origin_x=14.4`、`origin_z=-6.0`，零分歧），这才是"61/61 零违例"真正支撑的东西。换关卡时原点随站点自动得出，无需改代码——这才达成"删硬编码"的目标。

实现见 `ai/geometry.py`：`GridMapping.from_grid(grid, stations)`，多站点取众数防脏数据。

两个注意事项：

- 无站点可校准的关卡（或帧）回落到 `ORIGIN_X_DEFAULT=14.4` / `ORIGIN_Z_DEFAULT=-6.0` 兜底常量（Sushi_1_4 实测值，换关卡且无站点时会失真，故优先走站点校准）。
- `world.py:44` 注释称"已用站点+厨师数据验证"略有夸大：实测帧里厨师的 `interactions.gx/gz` 全为 `null`，厨师坐标实际没参与验证；校准只用站点。

**区分两件事**：

- **关卡常量**（上表）—— 本轮基本清干净。
- **关卡机制**（冰面、移动地板、传送门、老鼠等）—— 需要新代码，属 §10。

**灶具多样性：配方数据层已覆盖，Python 识别层没有。** 这点设计稿初版说成"已被数据驱动覆盖"，过头了：

- 配方数据确实含 6 种锅具（`Pot` / `FryingPan` / `DeepFatFryer` / `OvenTray` / `OvenCakeTin` / `Steamer`），`PLAN.md` §7.3 已确认。
- 但 Python 侧的锅具识别是**名字关键词匹配**：`_find_loose_pot` 按名字含 `pot` / `pan` 查找（`agent.py:456`），而 `AI_REVIEW.md:78` 自己标了 ⚠️「名字清单未在游戏实测」。`DeepFatFryer` / `OvenTray` / `OvenCakeTin` / `Steamer` 四种名字里既无 `pot` 也无 `pan`，换灶具关卡会直接漏。

**本轮要做的**：锅具识别改为**按站点类型 + 配方数据**判定，不做字符串前缀匹配。成本低，但必须做——§6.1 第 5、12 号 task 用"手持空锅 / 地上有锅"作为纯观测可行性来替代 `pot_cooked` / `dropped_cooked_pot` 两个记忆字段（现有代码 16 处引用），**这个替代的正确性完全依赖锅具识别可靠**。

"换关卡真能跑"仍需在新关卡实测验证，那是验证成本而非设计成本。

## 10. 未来工作：关卡机制与插件改造

本章记录**需要改 C# 插件才能支持**的关卡机制。本轮插件冻结，故全部列为未来工作。按"解除冻结后的实施顺序"排列。

通用原则：

- 插件侧只做**白盒读字段 + 加进状态 JSON**，不加判断逻辑。决策归 Python。
- 遵守 clean room 约束：只以游戏本体 `Assembly-CSharp.dll` 的公开类型 / 字段为事实来源，禁止复制 `Overcooked-2-HostUtilities` 源码。
- 新字段一律**可缺省**：Python 侧读不到就退化为当前行为，保证新旧插件可混用。
- 每项都需反编译确认类型 / 字段名后再实施（下表中的类型名来自 `PLAN.md` 既有笔记，**未逐一验证**，标 ⚠️）。

### 10.1 传送带（唯一的已知泛化残留）

**现状**：`world.py` 的 `BELTS` 按 `Sushi_1_4_2P` 手工标注格子与方向。`nodeMap` 把传送带格标为不可走（有占用者），靠该表补为可走；`_step_cost` 用它给逆向移动加代价 8。

**为什么必须改插件**：格子与方向只能从游戏对象读。`PLAN.md` §6 P3 已记结构：`TabletopConveyenceReceiver` 链（`m_item` / `m_receiving` / `ConveyToMe`）；`world.py` 注释另指向 `ConveyorStation.m_conveyanceDirectionXZ` ⚠️。

**插件改造**：枚举传送带站点，输出每条带的占用格列表与 `(dx, dz)` 方向，作为 `stations[]` 的新类型 `t:"conveyor"`（带 `dir` 字段）或独立的 `conveyors[]` 数组。

**Python 侧改动**：删除 `BELTS` 常量，`belt_cells` / `belt_dir` 改从状态构建。**其余逻辑不变**（`walkable()` 与 `_step_cost()` 已经按这两个集合写）。**解除插件冻结后，这是一处约十行的改动。**

### 10.2 冰面 / 打滑地板

**影响**：移动惯性改变——按住方向键后松开仍会滑行，"到位"判定与 `Approach` 的站位精度全部受影响；`Nudge` 的位移量也不再可预测。

**插件改造**：需先反编译定位地板材质 / 区域类型（⚠️ 类型名未知，需用 `ilspycmd` 搜索地面相关组件）。输出"打滑格集合"。

**Python 侧改动**：
- `world.walkable()` 不变（能走），但 `_step_cost` 对打滑格加代价。
- `Approach` 的到位判定需放宽阈值并增加"等滑停"（复用 `Settle` 原语）。
- `Nudge` 在打滑格上改用更短的按压。

### 10.3 移动地板 / 升降平台

**影响**：**最难的一类**——可走性变成时间函数，当前静态 `nodeMap` + BFS 的前提被打破。

**插件改造**：输出平台当前位置 + 运动周期 / 相位。

**Python 侧改动**：寻路需从"静态 BFS"升级为"**带时间维度的搜索**"（在格子 × 时间片上搜索，判断到达时平台是否在位）。这是真正的架构级改动，代价显著高于其他项。

**建议**：除非目标关卡必需，否则优先选择无移动地板的关卡。若必须支持，可先用保守退化策略——**把移动地板当永久不可走**，只走静态通路（可能绕远或无解，但不会掉下去）。

### 10.4 传送门 / 隔墙投掷

**影响**：网格图不再只有四邻接边——传送门是非相邻格之间的边；投掷可跨越台面送达。

**插件改造**：输出传送门的配对格。

**Python 侧改动**：BFS 的邻接函数增加"传送门边"；投掷需启用 §7.9 的 `Throw` 能力并新增一个 `ThrowTo(target)` 原语。注意投掷**是与 P1 协作的高价值动作**，接对话层后价值更高。

### 10.5 动态危险物（老鼠等）

**影响**：会偷走台面上的食材，破坏"放在台面上就安全"的假设（§7.4 的 `EnsureHandsFree` 依赖此假设）。

**插件改造**：输出其位置。

**Python 侧改动**：主要靠**已有机制自愈**——认领对账（§4.6）会发现料不见了，Planner 重新规划。额外可做的是打分层面避免把东西放在老鼠附近。**这一项对架构冲击最小。**

### 11.3 场景单测（新架构的工程红利）

用假 World 帧覆盖今天只能靠实机碰运气复现的场景：

| 场景 | 断言 |
|---|---|
| 端着黄瓜时着火 | 进 `Firefighting`；首节点 `EnsureHandsFree`；火灭后重新规划切黄瓜 |
| 订单被人类抢先送出 | 认领失效；改做下一单；半成品被复用或清理 |
| 饭熟了但无单需要 | 选 `RescueCooked`（端锅离灶），而非放任烧糊 |
| 两人同时想取同一锅 | ETA 近者优先；撞车后由后置校验转 FAILURE 并重算 |
| P1 持唯一灭火器 | **不进** `Firefighting`，留在 Normal 继续产出 |
| 糊锅 vs 快送完的餐 | 先送餐（两步可完成），再回头丢弃 |
| **离出餐口一步时另一锅 burning** | **不改主意**，先送完餐（验 §6.5 进度项） |
| **料被 P1 挡住一帧** | **不弃**当前承诺（验 §6.5 不可行迟滞） |
| **盘里被放错料** | 选 `ResetPlate`，而非反复放新盘占满拼装格 |
| **满盘在手时订单过期** | 不楔死：走 `ResetPlate` 或改配给其他同菜订单 |
| **火中被 P1 堵住** | 卡住守卫先生效（脱困），**不**死锁在 Firefighting |
| **两单都缺黄瓜** | 两个 `FetchToPlate` 是不同 task；P1 放入盘 B 不会让盘 A 的 task 误报成功 |
| 认领 TTL 到期 | 强制释放；资源可被重新分配（防泄漏兜底） |
| 分单模式归属为空 | **立刻退回接力**，不站着发呆 |

### 11.4 打分权重调参方法

初始权重取"量纲对齐"的朴素值，再用决策日志回放调整：

1. 实机跑若干局，收集 `trace` JSONL。
2. 回放时人工标注"这一拍我认为该做 X"，与 AI 实选对比。
3. 对分歧拍次查看 `terms` 拆解，判断是哪一项权重偏高 / 偏低。
4. 单项调整后重跑，比较 §11.5 的量化指标。

**不做自动调参 / 学习**（超出本轮范围，且会损害可解释性）。

### 11.5 完成标准

| 维度 | 标准 |
|---|---|
| 不退化 | **阶段 5 之后**：出餐数 / 得分中位数不低于阶段 0 基线中位数 −X%（N≥5 局，固定 P1 侧条件） |
| 多订单穿插 | 阶段 5 日志可见"下锅 → 期间推进别单 task → 回头取熟料" |
| 协同质量 | 阶段 6 回放测试台断言通过 + 人类陪玩无重复劳动、无站位僵持 |
| 可解释 | 任一拍的决策都能从 `trace` 回放出"为什么选它"及各候选的否决原因 |
| 健壮 | **30 分钟浸泡测试**：零模式锁死、零楔死认领、零残留按键、零认领泄漏 |
| 代码 | `agent.py` ≤ 100 行；无单个文件 > 400 行；无 `self.sub` 式共享字符串状态机 |

**浸泡测试是唯一能暴露认领泄漏的手段**（§4.1 的四个释放点若有遗漏，短局跑不出来，长局必然楔死），故列为硬标准。

文中的行数估计（如 `tasks.py` 约 100 行）仅为**量级参考**，不作验收标准——补上 §6.0 的参数化后必然超出。唯一的代码硬指标是上表最后一行。

### 11.6 风险与缓解

| 风险 | 缓解 |
|---|---|
| 打分涌现的决策不如写死顺序可预言 | 决策日志含 `terms` 拆解（§8.3）；承诺惯性防抖；场景单测覆盖关键判断 |
| 强制三段校验使每个动作多花 0.2–0.4 秒 | **已接受的取舍**：盲跳失败一次要重做整个流程，代价远大于零点几秒。多订单穿插可把确认等待填上 |
| 阶段 4 集成时多层同时出问题，难定位 | 阶段 1–3 已各自单测 / 冒烟；阶段 4 只接单订单 + 三个模式，面积最小 |
| P1 推断误判导致让位过度或抢活 | §6.7 的三层推断，置信度低时**只登记事实不预测**；惩罚而非硬 veto；confidence 衰减；显式指令硬覆盖；`--no-p1model` 可整层关闭 |
| 认领泄漏导致资源楔死 | §4.1 四个释放触发点 + TTL 兜底 + 30 分钟浸泡测试（§11.5） |
| 分单模式的 hold-and-wait 死锁 | §4.3 waiters 队列 + 超时让出并释放自有认领；**默认关闭**，录帧回放离线验证 |
| `RescueCooked` 依赖"锅离灶即停烧糊" | **已由用户确认该机制成立** |
| 多关卡未实测 | 本轮只承诺清理常量、不承诺跨关卡可用；关卡机制列 §10 |

## 12. 决策摘要

| 议题 | 结论 |
|---|---|
| 架构基底 | Arbiter + Planner + Executor 三层 + Blackboard；否决纯 HFSM+BT 与 Utility AI |
| 状态机的位置 | Arbiter（中断仲裁），**三行**模式表 + 卡住跨模式前置守卫 |
| 行为树的位置 | Executor，每 task 一棵小树，只管几步线性顺序 |
| 步骤顺序归属 | 任务间依赖归 Planner（可行性谓词涌现，**不建显式 DAG**）；动作内步骤归行为树 |
| 传输层 | 维持全量快照；不改事件推送。**插件推 5 Hz，Python 循环 20 Hz** |
| 模式判据 | 仅当"正常规划失效或不可能"才设模式；丢弃 / 抢收 / 锅找回全部下放为 task |
| 中断优雅退出 | halt 松键**并丢弃树**；抢占方树首 `EnsureHandsFree`；散落物靠无状态重算回收 |
| 执行可靠性 | 原语强制前后校验；失败一律交还 Planner；task 级 Timeout 兜底 |
| 资源管理 | 盘 / 灶 / 板 / 拼装格均为认领资源；**粒度 = `(资源, 动作)`**；四个释放触发点 + TTL 兜底；**可行性必须读 claims** |
| 协作模式 | 接力（默认）/ 分单（默认关闭），为 Planner 的一道过滤器。**"分工位"降级为对话层意图** |
| task 身份 | `(type, order_id, bound_resources, bound_item)`；谓词按绑定参数求值 |
| P1 推断 | 三层（事实 / 短程意图 / 显式告知）；**惩罚而非硬 veto**；confidence 衰减 |
| 承诺惯性 | 进度项抬高改选门槛 + 不可行需连续 M 拍才弃 |
| BT 库 | 维持手写 `bt.py`，删除未用的 `Parallel` |
| 可视化 | ASCII 决策日志 JSONL + `tree_viz.py` 离线回放 |
| 对话层 | 本轮仅预留三个注入口（Arbiter / 协作过滤 / 打分权重），不实现解析 |
| 插件 | 本轮冻结；关卡机制改造列入 §10 |
